## 阶段 0：仓库初始化

本次范围是导入原包、维护既有证据、建立本地开发入口与 CI，不包含新选股、扩池、调参或承诺完成联网补数。

- 导入真实 v4.0 程序、配置、必要基础数据与历史报告，校验两份冻结引擎 SHA-256。
- 建立 `AGENTS.md`、Claude / Cursor 入口、README、路线和扩容模板；不复制互相冲突的策略规则。
- 隔离可重拉的大体积行情、环境、凭据与构建产物，说明新克隆后如何恢复数据。
- 在干净检出条件下运行 Python / JS 工程验收；保存实际退出状态，并核验 GitHub CI。

完成证据是对应 Git 提交、冻结哈希和测试结果。CI 中的表头空文件及合成测试只验证工程行为，不构成真实全池数据通过。

## 阶段 1：补齐 16 只种子池真实数据

目标是使固定种子池能够开展可信的回放。优先处理原包已确认的 15 只股票缺口，保留已核验的牧原、指数、日历及公司行为底稿。

- 按 `universe.csv` 采集上市信息、未复权日线、真实停牌状态、开盘参考价、官方价格限制与权益事件。
- 对缺日、参考价冲突和权益到账异常逐项查原始证据；通过既有核验覆盖入口补充，不插值价格、不猜测停牌、不放宽输入校验。
- 保存数据来源、取得时间、覆盖范围、未解决项与采集回执；受支持的公司行为格式不足时明确阻断原因。

验收要求是新运行的股票和指数输入审计通过、上市后应有交易日零缺口，并明确 `stock_issues` 的本次值。ETF 可以独立保留缺口。网络或权限受阻时交付已取得的真实数据和缺口，不把失败写成“无需补齐”。

## 阶段 2：正式全池回放与诊断

固定 `policy.json`、种子池、引擎和执行规则，在数据验收通过后运行：

```bash
python fetch_v4_data.py
python run.py --confirm-seeds
```

先保留导入的原始报告和审计快照，再形成新的运行结果。正式交付应包含：

- `W1`、`W_Bear`、`W5`、`2026` 四个既定窗口的 R1 / R2 / R2_Bucket 结果、既有基准和执行压力情景，标明区间、费用与样本覆盖。
- 2026 月度换仓、实际持仓与桶暴露、单票体检、相关性矩阵；整手余量与买入前现金不足分别归因。
- 全池 Python / JS 逐笔成交与日净值按分对账，以及 2023-01-20 独立前缀核验。
- 报告与代码版本、数据快照、实际命令和退出状态对应；ETF 不足部分明确留空并解释分母。

当前种子池来自事后选择的现存龙头，历史回放仍有选择和幸存者偏差。合成 50 只配置测试、牧原单票结果、不同压力情景及重叠窗口均不能当作全池的独立盈利证据。阶段验收允许可信的阴性结果，不以盈利作为清零数据错误的条件。

## 阶段 3：16 → 50 只候选扩容研究

在固定种子池结果可解释后，按 [逐桶扩容模板](ai-prompts/bucket-expansion.md)开展研究。保留八桶规划意图，并先完成桶定义确认。50 是目标容量，不要求为了凑数降低证据质量。

扩容前记录候选依据、信息截止时点、选股方法和本轮比较目标；保留 16 只基线及每轮配置，不因看过结果而静默替换旧股票池。只通过配置和符合契约的数据扩容，冻结引擎与策略参数保持不变。

重点判断新增标的是否增加可解释的机会、降低集中度或改善实际资金利用，而非只比较最好一段收益。将当期行业地位、财务和相关性筛选用于旧历史时，明确标为回顾性研究；有充分的历史可得成员依据时，才另行定义对应的时点股票池实验。

## 阶段 4：宽基 ETF 日份额与独立雷达

ETF 采集可与股票补数并行，股票回放不以七只 ETF 全部齐备为前置条件。

按 `funds.csv` 补充实际日份额、价格或 NAV、成交额、份额折算和披露时点。历史官方日规模报表采用已批准的下一交易日可见假设，单列实际下载时点与带时间戳的实时样本。报告每只基金的上市边界、可用区间、覆盖率与窗口分母。

在足够的实际可得日覆盖下形成 2020 年以来的 5D / 20D 与条件前瞻诊断，说明有效样本及限制。ETF 雷达保持独立观测，份额变化不能识别具体投资者身份，也不自动变成轮动撮合条件。

## 后续自然前瞻

2026-11-20 之后的数据与冻结开发期分开维护。只有在规则、候选池与发布时点事先记录且结果未被用于反复选择时，才可称为相应的自然前瞻证据；晚于冻结日不等于自动未见样本。

前瞻记录应连接当时可得输入、信号、建议仓位与模拟可执行结果。是否进入实盘、资金规模和执行方式需要独立决定，本仓库初始化与研究命令不构成交易授权。
